# Preframe / 片策：完整 CT 审查（2026-08-19）

## 审查结论先说

**一句话定义**：这是给个人短视频创作者使用的、本地优先的内容生产工作台；它把一个选题推进成策划文档、镜头/素材准备、剪辑交接和人工辅助发布，而不是一个通用 SaaS 内容后台。

项目已经越过纯 Demo：核心生成、项目文件、镜头任务、剪辑准备和发布准备都已有真实读写及本机副作用。但它还不是能长期放心迭代的成熟产品，原因不在“功能少”，而在于 **主工作流没有成为唯一真相，且关键状态、测试和本机控制面边界还不够稳**。

当前最该做的不是再扩展平台、Agent、自动发布或数据看板，而是把已有能力收束为一个可恢复、可验证、可安全执行的「项目推进流」。

## 审查范围与证据

- 以 2026-08-19 的**实际脏工作树**为准，而非仅以 Git HEAD `20d8e1e` 为准；本次未改动业务源码。
- 阅读了前端页面/组件、76 个 Next Route Handler、`src/services`、Prompt/模型层、CLI、存储、Supabase、配置、测试与构建配置。
- 已复验：`npx tsc --noEmit`、`npm test`、`npm run build:web` 均通过。生产构建列出 76 个动态 API 路由。
- 安全动态验证已覆盖：LAN 可访问性、OAuth 外跳、模型连接测试对自选地址发请求、剪辑打开接口触发桌面动作。详见 [独立安全报告](/private/var/folders/qr/z3ytctj92sxb5vdysvvvx1mh0000gp/T/codex-security-scans/Preframe/20d8e1e_20260819T080114Z/report.md)。
- 未读取 `.env`、`.piance/` 或 `output/` 中的用户私密内容；外部 `PUBLISHER_LAB_ROOT` worker 也不在本仓库，列为 deferred，不能据此判断其自动化安全性。

## 1. 当前真实功能地图

### 已形成闭环

| 能力 | 实际路径 | 结论 |
| --- | --- | --- |
| 结构化策划生成 | `/create` -> `/api/generate` -> `contentWorkflow.generateProject` -> 临时目录 -> `output/<slug>` | 10 份文档按依赖/校验生成，支持取消、修复、部分失败状态；这是最成熟的主能力。 |
| 项目资料与文档处理 | 项目库 -> `/projects/[slug]` -> 查看、复制、下载、refine、单文档重生成 | 文档修改产生新文件而不覆盖原文件，结果可留存。 |
| 项目执行准备 | 项目详情 -> 镜头任务 -> 素材扫描/关联 -> `editing/` 工作区/Proxy/重连 | 不是静态 UI：会建立 manifest、符号链接、Proxy 队列、重连结果。 |
| 本地发布准备 | 发布中心 -> 会话/准备项 -> 平台文案/封面/导出/人工确认 | 已明确保留人工最终确认，不把“准备好”冒充“已发布”。 |
| 本地配置与轻量管理 | 模型、工作区、创作者档案、灵感、待办、阶段、回收站 | 文件系统 JSON/Markdown 持久化，对单人本机工具是合理的低基础设施方案。 |

### 部分实现，尚未闭合

| 能力 | 证据 | 缺口 |
| --- | --- | --- |
| 灵感转项目 | `IdeaInbox.tsx` 只把标题/备注塞进 `/create` query；`ideaManager.ts` 的 `markIdeaConverted` 没有调用方 | 项目创建成功后没有回写 Idea，所谓“已转项目”状态和反向跳转都不成立。 |
| 文档到镜头的同步 | `contentWorkflow.regenerateProjectDocuments` 写文档；`shots` 路由优先读 `project.json.shotTasks` | 重生成后旧镜头缓存不会自动失效/重建，阶段推断可能依据过时镜头。 |
| 阶段管理 | `projectStage.ts` 同时存在人工 `stage`、由 `publishData` 和 `shotTasks` 推断的阶段 | 存在多来源状态；例如发布数据可把阶段重新推到 `published`，人工归档语义不够清晰。 |
| CLI 对等性 | `generate` 复用编排；`refine`、`scan` 自行实现 | 同一个用户动作在 CLI/Web 的修复、命名、校验行为不同，维护时容易两边漂移。 |
| 发布自动化 | 仓库负责会话、worker 启动/取消和手动确认 | 外部 Python/browser worker 不在此仓库，端到端发布可靠性与安全性无法从当前代码确认。 |

### 隐藏能力，产品没有充分利用

- `project.json` 已保存 `stage`、`nextAction`、文档状态、镜头、发布数据；这些本可驱动一个连续的“下一步”界面，但今天分散在仪表盘、项目概览、镜头和发布中心。
- 已有本地草稿、原子 JSON 写入、临时项目目录、回收站、Proxy 复用、素材重连；它们是“可恢复工作流”的基础，但用户看不到统一的历史、恢复或异常待处理队列。
- 生成有阶段进度和文档质量状态，却没有在项目级持续呈现“哪个产物不可信、接下来要修什么”。

### 应删除、合并或停止扩张的东西

- `buildGeneratePrompt`、`parseGeneratedContent` 等旧生成链仍从 `generatePrompt.ts` 导出，但当前主生成已走单文档定义和验证链。它们会让下一次维护者修改错入口。
- `markIdeaConverted` 是孤立能力；要么接进创建成功回写，要么不要保留“已转项目”产品承诺。
- `web/app/globals.css` 已 8,257 行、含 46 处媒体查询。它还可运行，但继续堆局部样式会把每个 UI 小改动变成回归风险。
- 发布中心的“实验能力”已经很大（`PublishCenter.tsx` 1,015 行；`PublishSessionPanel.tsx` 816 行）。在核心工作流未收束前，不应继续加平台、账号类型或自动化按钮。

## 2. 产品判断：工具，而非尚未完成的 SaaS

### 核心用户和场景

目标用户不是“所有内容团队”，而是已经有题材、素材和发布账号的个人创作者；他/她打开片策，是为了把一条内容从模糊想法推进到今天能拍、能剪、能发的下一动作。

最有价值的承诺应是：**不要遗漏下一步，也不要在素材、脚本、剪辑与发布之间丢上下文。** 现有系统已经具备大部分执行材料；目前产品表达仍像数个强功能页面的集合。

### 产品现状

- **不是 Demo**：本地文件、模型调用、质量校验、编辑 manifest、ffmpeg Proxy、发布会话均为真实实现。
- **仍偏工具集**：创建、执行、发布分别有自己的数据/入口，用户需要自己判断“现在去哪里”。
- **接近可长期使用的个人工具，但不应对外托管**：本地单用户假设能解释文件系统和 OS 整合；一旦 LAN/公网部署，安全模型立即失效。

### 当前最大产品缺口

**没有一个以项目为中心的、可恢复的执行队列。**

现有页面告诉用户“有文档”“有镜头”“有发布中心”，但没有稳定地告诉用户：这个项目现在处在哪一阶段、哪个结果可信、哪个阻塞项必须先处理、完成它后下一件具体动作是什么。`stage`/`nextAction` 已经存在，却没有成为唯一产品主线。

## 3. UX / UI 审查

### 已做对的部分

- 页面按任务分区：创建、项目、灵感、待办、发布没有被塞进一个巨型表单。
- 生成过程具有阶段/文档级进度，且取消后会清理临时目录；项目详情的 refine 保留原文而非静默覆盖。
- 剪辑准备属于真实执行流，不是“为显得专业”做的空面板；素材重连和 Proxy 状态对高频创作有直接价值。
- 前端已有大量 `aria-*`/`role`/`htmlFor` 标记，并有 46 处响应式规则。基础意识存在。

### 影响真实使用的 UX 问题

1. **信息结构跟着模块走，没有跟着项目状态走。**
   `ProjectDetailView.tsx` 把文档、执行、概览放在模式切换里，关键“下一步”又分布在 `StagePanel`、`ShotExecutionWorkspace` 和 `PublishPanel`。用户需要自己拼接状态。
2. **反馈方式不统一。**
   组件各自维护 `error`、`notice`、局部 loading；`PublishCenter` 另有 toast。没有 app-level error boundary 或 route-level `error.tsx`/`loading.tsx`，网络失败后的恢复体验只能依赖每块组件自救。
3. **复杂动作与不可逆风险距离太近。**
   本地目录选择、打开 Finder/播放器/浏览器、启动发布 worker 都属于宿主机副作用，但 API 层的授权与确认边界不统一；这既是安全问题，也是 UX 信任问题。
4. **高密度界面已开始超过单组件承载上限。**
   发布、镜头素材、剪辑准备和侧栏都是 350--1,015 行级客户端组件。下一次需求只会继续增加局部状态和互相触发的刷新，交互回归会比视觉问题先发生。

### 无法从现有证据确认的 UX 项

- 没有看到可自动运行的键盘导航、屏幕阅读器或移动端视觉回归测试；不能据代码断言移动端/无障碍已真正通过。
- 没有真实创作者任务录屏或行为数据；不能量化首次完成率、哪一步停留最久、用户是否会二次回来。

## 4. 架构与数据层审查

### 可以保留

- **本地文件系统优先**：项目 Markdown + `project.json`、`.piance/*.json` 对当前单用户产品足够，避免为“产品化”提前上数据库。
- **服务层划分**：生成、项目、媒体、Proxy、发布等逻辑大多落在 `src/services`，Route Handler 通常较薄。
- **原子写入和局部锁**：`atomicJson.ts`、Proxy/manifest 锁能防止多个本机任务完成时直接丢状态。
- **生成临时目录再 final rename**：比直接写项目目录安全，取消/失败也有明确清理路径。

### 必须局部重构

| 位置 | 问题 | 为什么现在要处理 | 最小改法 |
| --- | --- | --- | --- |
| `src/services/contentWorkflow.ts` + `src/prompts/generatePrompt.ts` | 新旧生成路径并存 | 改 Prompt/校验时很容易改到未生效链路，AI 项目最怕“看起来改了，运行没变” | 删除不可达旧链，或隔离为明确的 legacy module；只保留一个可测试入口。 |
| `project.json` + `projectStage.ts` + shots/regen | 文档、镜头、阶段、发布是多来源状态 | 这是整个产品主线的真实性问题 | 引入轻量 `ProjectWorkflowState`：记录每个阶段的输入、产物、阻塞项、`updatedAt`，并将 shot cache 标为可失效派生数据。 |
| `web/components/publisher/PublishCenter.tsx` / `PublishSessionPanel.tsx` | 组件过大且请求/局部状态过密 | 发布是高副作用流程，难以测试和恢复 | 先抽出 query/state hook、会话操作 service、tab-level components；不改视觉和路由。 |
| `web/app/globals.css` | 8,257 行的叠加样式 | 每个新功能都可能与历史选择器/响应式规则冲突 | 先建立截图基线，再按页面域拆分 CSS；不要一次重写主题。 |
| `src/commands/refine.ts` / `scan.ts` | CLI 绕开 Web 已用的服务能力 | 同动作产物不一致，后续 bug 会双修 | 让 CLI 调用 `refineProjectFile`、`scanProjectAssets` 等已有公共服务。 |

### 现在不要动

- 不要把单机 JSON/Markdown 改成数据库、对象存储或多租户。它解决的是尚未发生的部署问题，会立即引入迁移、权限、备份、运维与成本。
- 不要“整体重写成状态管理库”。先把项目工作流状态收束为一个小领域对象；其余 UI 状态继续局部管理。
- 不要把发布 worker 收进本仓库，除非先决定它是产品承诺的一部分并能做端到端验收。

## 5. AI 审查

### AI 真正有价值的地方

从题材生成项目 brief、脚本、分镜、发布文案是模型擅长的非确定性创作劳动；它提供的是把创作者的空白页变成可编辑初稿的价值。`documentDefinitions`、分阶段生成、质量校验、repair/retry 是正确方向。

### 不应交给 AI 的地方

- 项目阶段、素材是否存在、Proxy 是否过期、文件重连、导出路径、发布确认都应该是确定性规则与用户确认。
- 不能用“AI 自动判断内容已可发布”替代清单和人工最终确认。

### 当前 AI 技术债

| 问题 | 影响 | 最小处理 |
| --- | --- | --- |
| `modelJson.ts` 的四阶段容错解析无独立测试 | 模型输出稍变就可能让核心生成不可预测 | 用录制的正常/围栏/损坏/多对象/注入式样本补纯单元测试。 |
| HTTP 请求缺统一超时和明确的重试策略 | 某些 provider 慢响应会让 CLI 或流程长时间挂住 | 每个模型调用加 deadline，针对网络/429/5xx 限次重试；不要对内容质量无限重试。 |
| Prompt/输出虽集中，但旧链仍存在 | 版本和运行路径容易分离 | 删除或隔离 legacy，并给当前 document definition 加 version。 |
| 模型调用结果与成本缺可观察记录 | 无法判断哪类文档最常失败、最耗时 | 先本地记录匿名化 job 指标：provider/model、文档号、耗时、repair 次数、结果；不记录正文和密钥。 |

## 6. 安全：先定部署边界，再谈修复

这不是泛泛的“本地明文 Key 有风险”结论。真正的首要问题是：系统具有文件系统、OS、模型密钥和发布 worker 权限，但当前开发服务曾监听 `*:3000`，LAN 地址访问成功，而多数管理 API 没有“调用者就是本机用户”的认证边界。

| 优先级 | 发现 | 已验证事实 | 处理原则 |
| --- | --- | --- | --- |
| P0 | 本机控制面可从 LAN 调用且多数管理 API 未授权 | 动态验证成功；可读取/改项目、配置、媒体、发布相关状态 | 近期先强制 loopback 绑定或显式本地 token；任何 LAN/公网模式必须统一认证、Origin/Host/CSRF 边界。 |
| P0 | 剪辑打开接口把任意请求路径交给宿主机桌面动作 | 动态验证将任意输入写进 macOS 剪贴板 | 不从请求体直接接受路径；由项目 slug + manifest 中的允许项解析。 |
| P0 | 模型连接测试可向攻击者指定地址发带凭据请求 | 动态验证已打到本地监听器 | 认证后使用、供应商 allowlist 或私网/loopback/DNS-rebinding 拦截，并避免复用已存 Key 给未知主机。 |
| P1 | OAuth callback 接受外部 `next` | 动态复现外部 307 跳转 | 仅接受同源相对路径并兜底到固定页面。 |
| P1 | `next` 等生产依赖落后于当前安全修复版本 | npm 生产审计有 4 个 high | 独立升级、回归构建和 API 路由，不能只改 lockfile。 |

**边界判断**：若它始终只绑定 loopback、由同一 macOS 账户使用，这是一组可以控制的本地工具风险；若要让同一 Wi-Fi 的手机、同事或公网访问，则这些问题不是“以后优化”，而是上线阻断项。完整证据、CWE 与动态记录在安全报告中。

## 7. 性能、可靠性与工程质量

### 已经出现的问题

- 生成 job、IP 窗口、用户窗口保存在 `generate/route.ts` 的进程内 Map，未见 TTL 清理；长期运行会增长，重启则任务状态丢失。
- `npm test` 当前只执行质量状态、Proxy 与素材重连 3 组。`shotTaskApi.test.ts`、`shotTaskBuilder.test.ts` 和真实 `acceptEditing.mts` 未进入脚本；因此测试绿不能覆盖生成 -> 镜头 -> 剪辑 -> 发布主链。
- 没有 CI workflow、格式/lint 脚本、错误边界或集中化错误监控。AI 辅助修改后，最容易“被改坏且回不去”的就是生成/解析/状态同步链，因为它们的行为没有被端到端锁住。
- `process.cwd()` 仍是 `.piance`、profile、output、publisher root 等多处路径基准。从不同目录启动时可能读写到不同数据根。

### 尚未出现、但要在下一阶段留意的事

- 项目数和媒体量大后，仪表盘的磁盘扫描、媒体 metadata 扫描、浏览器大列表渲染会变慢；此刻不需要 Redis、队列或数据库，只要先做按需扫描/缓存失效和列表分页/虚拟化评估。
- 多个生成/Proxy/发布进程跨重启恢复需要持久化 job 状态；只有真正出现中断恢复诉求时，再把 job 移出内存。

### 工程基线建议

1. 保持现有三件套，并把 `shotTask`、API 路由契约、生成解析 fixture 测试纳入 `npm test`。
2. 加一个最小 GitHub Actions：Node 固定版本，跑 `tsc`、`test`、`build:web`。不需要部署流水线。
3. 给路由级错误/加载增加统一边界，并为文件/OS/worker 动作使用同一错误分类与可重试提示。
4. 让 workspace root 成为一个显式配置值，启动时记录并展示实际根目录；避免所有模块各自推断 `cwd`。

## 8. 优先级：有限投入时该做什么

### P0：必须先修

| 事项 | 解决什么 | 用户收益 | 成本 | 技术风险 | 与核心关系 |
| --- | --- | ---: | ---: | ---: | --- |
| 收紧本机控制面与路径能力 | LAN 未授权、任意 host action、模型 SSRF | 高 | 中 | 中 | 最高 |
| 统一项目工作流状态并使派生缓存失效 | 文档/镜头/阶段/发布状态漂移 | 高 | 中 | 中 | 最高 |
| 清掉旧生成链并补生成/解析/镜头契约测试 | AI 改坏后无法识别 | 高 | 中 | 低 | 最高 |

### P1：最值得开发

| 功能 | 解决什么问题 | 用户收益 | 开发成本 | 技术风险 | 与核心产品关系 | 优先级 |
| --- | --- | ---: | ---: | ---: | --- |
| 项目推进流（唯一“下一步”） | 功能页多、用户自己拼接流程 | 很高 | 中 | 中 | 直接承接核心承诺 | P1 |
| 可靠生成层（超时、有限重试、可见失败、恢复） | 模型慢/坏输出造成悬挂或不确定结果 | 很高 | 中 | 中 | 直接 | P1 |
| 项目健康检查 | 找出缺文档、过时镜头、丢素材、未准备发布项 | 高 | 中 | 低 | 直接 | P1 |

**“一个功能顶十个”的机会：项目推进流。**

它不是新页面堆卡片，而是使用现有 `stage`、`nextAction`、documentsStatus、shotTasks、editing manifest、publish readiness 生成一个单一项目状态：`当前阶段`、`阻塞项`、`下一件动作`、`已完成证据`。项目详情首屏、首页“今天”、待办、发布入口都读它。这样会同时解决导航、空状态、状态同步、提醒、恢复、发布前检查和测试锚点，而不增加另一套数据。

最小版本：只读 `ProjectWorkflowSummary`，不自动改阶段；用户点“完成/重建/继续”才调用现有 API。完整版本才考虑历史记录和自动建议。

### P2：有价值，但可以以后做

| 功能 | 原因 |
| --- | --- |
| 小型项目恢复/历史记录 | 在用户真实遇到中断、误改、素材失效后价值很高；先记录关键状态变更即可。 |
| 本地 Keychain 存储 | 多人共用机器或桌面打包前需要；先修服务暴露和出站边界。 |
| 发布平台适配完善 | 只在一个平台的手工闭环稳定后扩展，避免每个平台复制状态与 UI。 |
| 媒体大库优化 | 以真实项目规模触发，不预设分布式架构。 |

### P3：现在明确不要做

| 不做的事 | 为什么不做 |
| --- | --- |
| SaaS 多租户、对象存储、后台管理系统 | 当前定位是本地单人工具；会把安全、迁移、运维复杂度提前十倍。 |
| RAG、Agent 编排、MCP 工作流 | 不解决“项目下一步不明确”和状态漂移；只会制造更多不确定性。 |
| 自动真实发布/无人值守账号操作 | 当前外部 worker 尚未仓库内验收，且平台风险和误发成本高。 |
| 更多 Dashboard 图表、成就系统、社交功能 | 用户需要推进一条内容，不是观看更多统计。 |
| 大规模状态管理重写或 CSS 全盘重写 | 先收束领域状态、建立截图/测试基线；整体重写几乎没有即时用户收益。 |

## 9. 现实 Roadmap（单人 + AI Coding）

### 今天

1. **P0：限制服务到 loopback，并修复任意路径桌面动作、模型连接测试和 OAuth 外跳。** 因为这些能力已经能碰到本机文件、剪贴板、浏览器和密钥，不能等功能更复杂。
2. **修复灵感回写、镜头缓存失效和阶段优先级。** 因为这是用户已经看得见的错误状态，不是技术洁癖。
3. **把生成/解析/镜头测试纳入唯一 `npm test`。** 因为接下来任何 AI 辅助改动都依赖这条安全网。

### 接下来 3 天

1. 定义 `ProjectWorkflowSummary` 和一组 fixture，先只读汇总当前/阻塞/下一步。
2. 在项目详情首屏和首页今日推进使用它；不新增第二套持久化数据。
3. 把旧生成链和 CLI 重复路径收束到当前服务层，并加模型超时、有限重试。

### 接下来 7 天

1. 建立项目健康检查：文档有效性、镜头是否过时、素材是否丢失、editing manifest、发布前必填项。
2. 拆分发布中心的状态/请求层，保留现有 UI 行为；将外部 worker 标记为实验能力并保留显式人工确认。
3. 建立 CI 和最小错误边界，加入一个真实的“生成失败 -> 修复/重试 -> 可恢复”测试。

### 接下来 30 天

1. 跟 3--5 位真实创作者做一次完整内容生产观察，记录从灵感到发布准备的卡点与时长。
2. 只针对实际卡点完善项目历史/恢复、平台文案变体或媒体扫描性能。
3. 依据部署决定路线：继续桌面/本地工具则补打包、Keychain、备份说明；决定做远程协作才另立项目处理认证、多租户和存储迁移。

## 10. 最终评分与唯一选择

| 维度 | 分数 | 判断 |
| --- | ---: | --- |
| 当前项目完成度 | **68 / 100** | 核心能力广且多数真实可运行，但工作流闭合和安全边界没完成。 |
| 产品完整度 | **63 / 100** | 已从选题走到发布准备，却缺唯一的推进主线。 |
| 代码质量 | **58 / 100** | 服务层与本地持久化基础不错；旧链、巨型组件、测试覆盖和 CSS 债明显。 |
| 架构健康度 | **61 / 100** | 可以局部收束，无需推倒重来；状态多源是最大结构风险。 |
| UX | **60 / 100** | 任务页面和局部反馈可用，但用户需要自己理解流程。 |
| 继续开发潜力 | **80 / 100** | 现有真实能力足够支撑很强的个人创作工具，前提是停止功能蔓延。 |

1. **当前最大的一个问题**：项目状态没有单一真相，用户和代码都要在多个模块之间猜“下一步”。
2. **当前最值得增加的一个功能**：项目推进流（当前阶段、阻塞项、下一步、完成证据）。
3. **当前最值得优化的一处架构**：以 `ProjectWorkflowSummary` 收束文档、镜头、素材、剪辑与发布的派生状态。
4. **现在最不应该做的事情**：把它提前 SaaS 化或继续扩展无人值守发布自动化。
