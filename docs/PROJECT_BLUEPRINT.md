# 片策项目蓝图

最后更新：2026-08-28

本文档是当前仓库内容生成链路的事实来源。历史审计文档只记录当时状态，不应覆盖本文件。

## 1. 产品定位

片策是一个本地运行的短视频内容生产工作台。它不是“批量生成策划文章”的工具，而是把一个选题推进成：

1. 一套明确且可验收的创作约束；
2. 一份可以直接提词、拍摄、做字幕和剪辑的执行稿；
3. 一张可发布、可记录结果、可持续复盘的运营卡。

核心目标是减少跨文档复制和人工同步，让同一个项目只有一套最终口径。

## 2. 新项目的三份核心工作稿

文档定义位于 `src/utils/documentDefinitions.ts`。

### 01_创作简报.md

唯一的创作约束真源，包含：

- 目标与用户；
- 核心观点；
- 内容结构；
- 目标时长、建议字数、必保留项和禁用表达；
- 事实与平台风险边界；
- 必须由人确认的事实、素材或取舍。

它不展开逐字稿、分镜或发布话术。

### 02_拍摄执行稿.md

拍摄、提词、字幕和剪辑共用的唯一锁稿真源，包含：

- 执行摘要；
- 一版最终逐字口播稿；
- 固定列的镜头执行表：`时间｜最终口播｜画面/动作｜字幕重点｜B-roll/素材｜拍摄状态`；
- 场景与设备；
- 素材与替代方案；
- 拍摄风险；
- 锁稿检查。

系统必须在交付前完成时长压缩、禁用表达清理和跨段落对齐，不能把“再删、再压缩、再同步”留给用户。

### 03_发布与复盘.md

发布前后共用的运营卡，包含：

- 一个最终主标题和一个最终封面方案；
- 平台发布文案；
- 一条置顶评论和少量选题专属补充回复；
- 发布时间、链接和版本记录；
- 24 小时、72 小时、7 天真实数据回收；
- 基于真实数据决定的重剪、二创和延展动作。

未知数据必须写“发布后填写”，不得虚构表现或“高频评论”。账号级合作私信、杠精处理、粉丝群规则不在每个项目重复生成。

## 3. 单一真源与依赖关系

新生成流程严格按顺序执行：

```text
projectBrief
  ↓
01_创作简报
  ↓
02_拍摄执行稿
  ↓
03_发布与复盘
```

依赖定义位于 `src/prompts/enhancePrompt.ts`。

- 02 只读取 01；
- 03 只读取 01 和 02；
- 下游不得重新发明观点、旧表达或未核实事实；
- 重生成上游文档时，受影响的下游文档必须一起重生成；
- 镜头任务直接从 02 的镜头执行表解析，不再从多份文档拼接。

## 4. 自动质量门

用户不再收到独立的“内容质检报告”。质检属于系统内部动作：

```text
生成 → 结构校验 → 一致性/可执行性校验 → 自动修复一次 → 写入
```

当前质量门至少检查：

- 必需标题和最小有效内容；
- 占位语与明显 AI 套话；
- 拍摄执行稿是否符合目标时长；
- 镜头执行表是否具有固定列和至少三个执行段；
- 初始拍摄状态是否统一为“未拍”；
- 是否仍包含“后续再压缩、不能直接拍”等返工指令；
- 锁稿检查是否明确“可直接拍”；
- projectBrief 中的禁用表达是否重新出现在最终口播或发布文案；
- 发布记录是否把未知信息标为“发布后填写”；
- 数据复盘是否包含 24 小时、72 小时和 7 天节点；
- 是否混入虚构高频评论或账号级通用私信话术。

质量门通过后，`project.json` 写入：

```json
{
  "workflowVersion": 2,
  "workflowModel": "three-document-single-source",
  "qualityGate": {
    "mode": "automatic-repair",
    "passed": true
  }
}
```

## 5. 生成与重生成

核心入口：

- Web：`POST /api/generate`
- CLI：`npm run generate`
- 服务：`src/services/contentWorkflow.ts`

生成过程：

1. 创建临时项目目录；
2. 生成包含核心观点、结构、目标时长、必保留项、禁用表达和风险边界的 `projectBrief`；
3. 顺序生成三份核心工作稿；
4. 每份文档失败后最多自动修复一次；
5. 上游失败时停止生成下游，避免制造孤立文档；
6. 全部结果和质量状态写入 `project.json`；
7. 原子移动到正式项目目录；
8. 从 02 构建结构化镜头任务。

重生成规则：

- 重生成 01：同时重生成 02、03；
- 重生成 02：同时重生成 03；
- 重生成 03：只重生成 03；
- 原文件进入版本归档，避免静默覆盖。

## 6. 拍摄复盘

拍摄复盘不再生成“脚本、分镜、拍摄清单、成片执行稿”四份修订文件。

新的复盘修订只生成：

- `02_拍摄执行稿.md`

模型直接把现场证据同步回最终逐字稿、镜头执行表、素材、替代方案和拍摄风险。应用修订时继续保留可匹配镜头的拍摄状态、素材关系和备注。

## 7. 发布与长期维护

发布不是流程终点。03 为以下数据预留真实回填位置：

- 发布平台、时间、链接和版本；
- 24 小时表现；
- 72 小时表现；
- 7 天表现；
- 钩子留存、完播、互动、评论主题；
- 是否重剪、重发、二创或发展为系列。

后续应继续把真实复盘写回账号记忆和选题策略，而不是在发布前编造预测数据。

## 8. 历史项目兼容

历史 6/8/10 文档项目继续支持：

- 浏览与导出；
- 单文件修改；
- 旧分镜/拍摄清单/成片执行稿解析；
- 旧视觉提示词封面生成；
- 历史项目自己的完成度展示。

旧文件名登记在 `LEGACY_DOCUMENT_DEFINITIONS`。新项目不会再生成这些文件，也不会把它们计入三文档完整度。

## 9. 历史项目迁移

历史项目不会在读取时静默改写。项目页会显示“历史项目”，用户点击迁移后调用 `POST /api/projects/[slug]/migrate`：

1. 读取旧文档和历史 `projectBrief`；
2. 基于旧内容生成三份新工作稿；
3. 通过新版结构、时长、口径和可执行性质量门；
4. 将旧文档写入 `.versions/`，原因标记为 `workflow-migration`；
5. 删除项目根目录中的旧版主文件，写入三份新版文件；
6. 在 `project.json` 写入 `workflowVersion: 2`、迁移记录和已归档文件列表；
7. 重新解析镜头任务。

任意模型或质量门失败时不会执行删除旧文件的步骤。

## 10. 验收命令

```bash
npx tsc --noEmit
npm test
npm run build:web
```

新生成逻辑的最低验收标准：

- 新项目只出现三份核心 Markdown；
- 02 能直接解析成镜头任务；
- 不再生成用户可见质检报告；
- 禁用表达不会重新出现在最终口播和发布文案；
- 02 不含让用户继续压缩或返工的指令；
- 03 不虚构评论和发布数据；
- 历史项目仍能打开；
- TypeScript、测试和 Web 生产构建通过。
